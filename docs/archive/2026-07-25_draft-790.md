# Bulk Email + Bulk SMS Campaigns — Design Spec

Status: **design only, not built.** Written 2026-07-25 for hand-off to a build session.
Target: NPU Hub v2 (`htfrfaxlcuyawtlztxxm`). Org-scoped for Neuro Progeny + Sensorium.

## 0. The reachability blocker — resolved

This work was parked because the audience looked unreachable. The investigation says the
audience is *mislabelled*, not unreachable, and that there is a second, worse bug pointing
the other way.

### 0.1 `email_consent` defaults false

```sql
email_consent BOOLEAN NOT NULL DEFAULT false   -- crm_001_complete_schema.sql:62
sms_consent   BOOLEAN NOT NULL DEFAULT false
```

Live counts (2026-07-25):

| metric | value |
|---|---|
| contacts | 306 |
| has non-empty email | 128 |
| `email_consent = true` | 27 |
| `email_consent = false` | 279 |
| false **with** `email_unsubscribed_at` set (real opt-out) | **0** |
| false with both consent timestamps NULL (never touched) | **279** |
| true **with** `email_consent_at` set (provenance) | **0** |
| consent true AND email present | 12 |
| `sms_consent = true` | 8 (7 with a phone) |

**Conclusion: no contact has ever opted out of email. All 279 falses are the column
default.** The blocker was a schema default, not audience rejection.

### 0.2 The inverse bug — unprovenanced `true`

`src/app/(dashboard)/crm/contacts/page.tsx:398-399` hard-codes on every manual contact
create:

```ts
sms_consent: false,
email_consent: true,     // <-- no timestamp, no source, no evidence
```

The only code path that stamps `email_consent_at` is `POST /api/contacts/consent`
(`route.ts:27`), and no row in the database bears its fingerprint. So all 27 "consented"
contacts are consent-marked with **zero evidence of consent**. Under CAN-SPAM that is
survivable; under GDPR/CASL it is not defensible, because we cannot produce the record.

`src/components/crm/contact-detail.tsx` has an SMS consent toggle (line 1894) and **no
email consent toggle**. There is currently no UI to fix either direction.

### 0.3 Who the contacts actually are

`source` breakdown makes the legal picture concrete:

| source class | ~count | lawful basis for bulk email |
|---|---|---|
| scraped IG/LinkedIn profile URLs | ~120 | **none** — no relationship, no opt-in |
| `xregulation` | 24 | depends on the xreg participant agreement — verify |
| `media_appearance` | 17 | individual, case-by-case |
| `Import` / city names (conference lists) | ~30 | none without provenance |
| `stripe`, `Website`, `Podcast`, `Workshop`, `admin`, `manual_ecr` | ~10 | yes — existing business relationship |
| `(null)` | 85 | unknown — must be triaged |

**Flipping the default does not manufacture a lawful basis.** The honest reachable
universe is roughly:

- **Now (transactional/lifecycle):** ~10 contacts with a real relationship.
- **After a re-permission campaign:** up to ~120 with a deliverable address, minus
  whatever fraction never opts in (assume 5-20% conversion).
- **Never, without new consent:** the scraped prospecting list.

### 0.4 Remediation — must land before any campaign send

**R1. Stop writing consent without evidence.** Remove the hard-coded
`email_consent: true` from the contact-create form. New contacts default false like
everything else.

**R2. Backfill provenance, do not backfill consent.** Do **not** mass-flip 279 rows to
true. Instead add the columns in §2.1 and mark the existing 27 trues as
`consent_source = 'unverified_legacy'`. The consent gate (§4) treats
`unverified_legacy` as **not sendable for marketing**, sendable for transactional. This
is the whole point: the design refuses to inherit a lie.

**R3. Malformed-email sweep.** Small and tractable — 128 addressed contacts, 10 problems:

| id (prefix) | name | email | issue |
|---|---|---|---|
| `787bd1c5` | Rachel Kimmel | `mailto:rachel17313@gmail.com` | mailto: prefix, consent=true |
| `08777c35` | Ella Brown | `Test` | not an address |
| `395c1ad8` / `5c438ffe` | shane test / Shane Test | `test@gmail.com` ×2 | test data + duplicate |
| `5921c286` | Cameron Allen | `cameron.s.allen+buyertest1@gmail.com` | own test buyer |
| 6 rows | — | mixed case (`AGTherapies@`, `Brent@`, …) | normalize to lower |

Also: 128 addresses collapse to **118 distinct** when normalized — 10 duplicate addresses
across separate contact rows. Bulk send must dedupe on normalized address, not contact id
(§5.3), or those people get the same email twice.

Sweep = a migration that normalizes (`lower(btrim(replace(email,'mailto:','')))`), nulls
the non-addresses, and tags the test rows. Do not delete contacts.

**R4. Re-permission campaign is the first campaign built.** Single-send, to every contact
with a deliverable address and a defensible relationship, asking them to opt in. Its
own reply-to, its own landing page (§4.4). Everything else in this spec is downstream of
it succeeding.

> **Every section below is marked with its dependency on R1-R4.** Nothing that sends to a
> list can ship before R1+R3. Nothing marketing-classified can ship before R4.

### 1.2 Dead code — schema drift, must be deleted or rewritten

`email/send`, `email/campaign/launch`, and `email/campaign/process-queue` were written
against a schema that was **never applied**. Live vs. code:

| code references | live schema actually has |
|---|---|
| `email_sends.to_email`, `.batch_number`, `.provider_message_id` | none of them; it has `external_message_id` |
| `email_campaigns.filter_criteria`, `.batch_size` | `filter_tags`, `filter_stages`, `exclude_tags` |

| `org_email_daily_stats.date`, `.sent_count` | `stat_date`, `sent` |
| `contacts.pipeline_stage` filter | column is `pipeline` |

`launch` would throw on insert; `process-queue` reads `config.webhook_url` (undefined) and
`continue`s. **`process-queue` is on a `* * * * *` Vercel cron** (`vercel.json`) — it is a
silent no-op only because `email_campaigns` has 0 rows. The moment anyone inserts a campaign
row it starts erroring every minute.

**Decision: delete all three routes and the `process-queue` cron entry.** This spec replaces
them. Do not try to repair them incrementally.

`api/sequences/process-step` is likewise drifted (reads `config.webhook_url`; calls
env-level `sendSms` from `lib/twilio`, bypassing org number routing entirely) and
`sequences`/`sequence_steps`/`sequence_enrollments` all have **0 rows** — the "real drip
engine" is code-only and has never run.

### 1.3 `email_sends` is not logging — root cause

`email_sends.campaign_id` is **NOT NULL**. `stage-emails/route.ts:244` inserts a stage-email
log row with `campaign_id` omitted → NULL → `23502` → caught by
`if (logError) console.error(...)` and discarded. Three confirmed stage emails, zero ledger
rows. The route's own comment blames the `email_sends_via_campaign` RLS policy; that *was*
a cause and was fixed by switching to the admin client, but the NOT NULL constraint is the
live cause and is still there.

Consequence: `calculateHealthScore()` (`lib/crm-server.ts:418-428`) reads `email_sends` for
open rate, gets an empty array, and every contact scores 0% on the 15% engagement weight.

`email_sends` also has **no `org_id`** — it cannot be org-scoped for white-label as it stands.

## 2. Data model

### 2.1 Consent — new columns on `contacts` (dep: R1, R2)

```sql
alter table contacts
  add column email_consent_source text,      -- see enum below
  add column email_consent_evidence jsonb,   -- {ip, user_agent, form_url, submitted_at} | {imported_from, note}
  add column sms_consent_source text,
  add column sms_consent_evidence jsonb;
```

`*_consent_source` values, in ascending trust order:

| value | meaning | marketing-sendable |
|---|---|---|
| `unverified_legacy` | pre-existing `true` with no provenance (the 27) | **no** |
| `staff_attested` | a staff member ticked a box and named the basis | no (marketing), yes (transactional) |
| `implied_transaction` | Stripe purchase / enrolled client | yes, transactional + service-related only |
| `double_optin` | clicked a confirmation link | **yes** |
| `web_form` | submitted a form with a consent checkbox, evidence captured | yes |

Keep `email_consent boolean` as the coarse gate (existing code reads it), but the campaign
consent gate (§4) reads `source` as well. This is additive; nothing existing breaks.

`sms_consent_at` is currently **never written** — `/api/contacts/consent` stamps
`email_consent_at` but not its SMS counterpart (`route.ts:24-28`). Fix in the same migration.

### 2.2 Campaigns

```sql
create table campaigns (
  id            uuid primary key default gen_random_uuid(),
  org_id        uuid not null references organizations(id) on delete cascade,
  name          text not null,
  channel       text not null check (channel in ('email','sms')),
  -- classification drives the consent gate. Not cosmetic.
  intent        text not null check (intent in ('marketing','transactional','service')),

  subject       text,          -- email only
  body          text not null, -- html for email, plain for sms
  body_text     text,          -- email plaintext alternative
  from_name     text,
  reply_to      text,

  audience      jsonb not null default '{}'::jsonb,  -- see §3
  status        text not null default 'draft'
                  check (status in ('draft','scheduled','building','sending','paused','completed','cancelled','failed')),

  scheduled_at  timestamptz,
  started_at    timestamptz,
  completed_at  timestamptz,

  throttle_per_minute int not null default 20,
  daily_cap           int,

  created_by uuid references team_members(id),   -- NOT auth.users; resolve first
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

`created_by` FKs `team_members(id)`, matching the house rule that user-attribution columns
resolve `auth.uid()` → `team_members.id` rather than storing the auth id.

**`intent` is load-bearing.** `marketing` requires `double_optin` or `web_form`.
`transactional`/`service` accept `implied_transaction` and `staff_attested`. The gate is a
DB function (§4.1), not a route-level `if`.

### 2.3 Recipients — the claim ledger

This is `stage_email_sends` generalized. Same claim-not-check discipline, same partial
unique index, same skip persistence.

```sql
create table campaign_recipients (
  id          uuid primary key default gen_random_uuid(),
  campaign_id uuid not null references campaigns(id) on delete cascade,
  org_id      uuid not null references organizations(id) on delete cascade,
  contact_id  uuid not null references contacts(id) on delete cascade,

  -- resolved and FROZEN at build time, so a mid-flight contact edit
  -- cannot redirect an in-flight send
  dest        text not null,          -- normalized email or E.164
  dest_hash   text not null,          -- lower(btrim(dest)) — the dedupe key

  status      text not null default 'pending'
                check (status in ('pending','claimed','sent','delivered','failed','skipped','bounced')),
  skip_reason text,
  attempt     int not null default 0,

  provider_message_id text,
  error_message       text,

  claimed_at   timestamptz,
  sent_at      timestamptz,
  delivered_at timestamptz,
  opened_at    timestamptz,
  clicked_at   timestamptz,
  bounced_at   timestamptz,
  created_at   timestamptz not null default now()
);

-- THE GUARD. Mirrors stage_email_sends_once: only in-flight and successful
-- states occupy the slot, so a 'failed' or 'skipped' row never permanently
-- bars a retry, and a re-build cannot double-enqueue.
create unique index campaign_recipients_once
  on campaign_recipients (campaign_id, dest_hash)
  where status in ('claimed','sent','delivered');

-- one row per contact per campaign regardless of address churn
create unique index campaign_recipients_contact_once
  on campaign_recipients (campaign_id, contact_id);

create index campaign_recipients_claimable
  on campaign_recipients (campaign_id, status) where status = 'pending';
create index campaign_recipients_stale
  on campaign_recipients (status, claimed_at) where status = 'claimed';
```

Why `dest_hash` and not `contact_id` in the guard: the 10 duplicate addresses in §0.4.
Two contact rows sharing `melissa@example.com` must produce **one** send.

Why freeze `dest` at build time: if the send loop re-reads `contacts.email` at send time,
an edit between build and send silently redirects the message.

### 2.4 Suppression

`do_not_contact_list` already exists (org-scoped, phone + email, 0 rows). Extend rather
than replace:

```sql
alter table do_not_contact_list
  add column scope text not null default 'all'
    check (scope in ('all','marketing')),   -- unsub from marketing ≠ block receipts
  add column source text,                   -- 'unsubscribe_link' | 'complaint' | 'bounce_hard' | 'sms_stop' | 'manual'
  add column campaign_id uuid references campaigns(id) on delete set null;

create unique index dnc_org_email on do_not_contact_list (org_id, lower(email)) where email is not null;
create unique index dnc_org_phone on do_not_contact_list (org_id, phone)        where phone is not null;
```

`isDNC()` in `lib/crm-server.ts:13-20` builds an `.or()` string by interpolating
`contact.phone`/`contact.email` unescaped — with a null phone this produces
`phone.eq.null,email.eq.x`. Rewrite it against the new unique indexes and make it
scope-aware while you are in there.

### 2.5 Send ledger — fixing `email_sends`

Two options; **take B.**

- **A.** Make `email_sends.campaign_id` nullable and add `org_id`. Minimal, but leaves the
  ledger shaped around campaigns when most rows are stage/1:1 sends.
- **B (recommended).** Make `campaign_recipients` the campaign ledger, and create a
  **unified `message_sends`** view/table that `calculateHealthScore()` reads:

```sql
alter table email_sends alter column campaign_id drop not null;
alter table email_sends add column org_id uuid references organizations(id);
alter table email_sends add column channel text not null default 'email';
alter table email_sends add column dest text;
alter table email_sends add column source text;  -- 'campaign' | 'stage' | 'manual' | 'sequence'
```

…then have **every** send path write one `email_sends` row, and repoint
`calculateHealthScore()` at it. The single most important line in this whole spec:

> **A send that is not in the ledger did not happen.** The ledger write must be part of the
> same code path as the send finalization, and its error must be surfaced, not
> `console.error`'d. The current `if (logError) console.error(...)` at
> `stage-emails/route.ts:251` is exactly how three real sends vanished.

Backfill the 3 existing `stage_email_sends` rows with `status='sent'` into `email_sends`
so scoring has something to read on day one.

## 3. Audience definition

`campaigns.audience` jsonb, evaluated **once at build time** into `campaign_recipients`.
Never re-evaluated mid-flight.

```jsonc
{
  "include": {
    "tags":            ["mastermind-2026"],
    "pipeline":        ["enrolled"],
    "sources":         ["Website", "stripe"],
    "lifecycle_label": ["client"],
    "assigned_to":     ["<team_member_id>"]
  },
  "exclude": {
    "tags": ["do-not-market"],
    "contact_ids": []
  },
  "test_mode": { "enabled": true, "limit": 5 }
}
```

Rules:

- Every predicate ANDs. `include.*` arrays OR within themselves.
- `org_id = campaign.org_id` and `merged_into_id is null` are **implicit and
  non-overridable** (the merge-repoint problem in the contact-merge work means a merged
  contact can still hold a stale address).
- Build produces a **preview count and a downloadable list** before `status` leaves
  `draft`. Nobody launches blind.
- `test_mode` sends to N staff addresses only, writing real recipient rows with
  `skip_reason = 'test_mode_excluded'` for everyone else — so the test is auditable.

## 4. Consent enforcement

**Requirement: it must be structurally impossible to send to a contact without valid
per-channel consent.** Not "the route checks." Three layers, each independently sufficient.

### 4.1 Layer 1 — DB function, single source of truth

```sql
create or replace function is_sendable(
  p_contact_id uuid,
  p_channel    text,     -- 'email' | 'sms'
  p_intent     text      -- 'marketing' | 'transactional' | 'service'
) returns table (ok boolean, reason text)
language plpgsql stable as $$
-- Order of checks, fail-closed at every step:
--   1. contact exists, merged_into_id is null            -> 'merged_contact'
--   2. do_not_contact = false                            -> 'dnc_flag'
--   3. not in do_not_contact_list for (org, dest, scope)  -> 'suppressed'
--   4. channel consent boolean is true                   -> 'no_consent'
--   5. consent_source is adequate for intent:
--        marketing  requires source in ('double_optin','web_form')
--        service    additionally allows 'implied_transaction'
--        transactional additionally allows 'staff_attested'
--        'unverified_legacy' NEVER satisfies marketing    -> 'consent_unprovenanced'
--   6. dest present and passes format check               -> 'no_address' | 'malformed_address'
--   7. channel='sms': dest is valid E.164                 -> 'malformed_phone'
$$;
```

Every gate lives here. The audience builder, the send worker, and any future 1:1 route all
call the same function, so they cannot drift apart.

### 4.2 Layer 2 — build-time gate with durable skips

The audience builder calls `is_sendable()` per contact and writes a
`campaign_recipients` row **for every evaluated contact**, `status='pending'` or
`status='skipped'` with `skip_reason` = the function's reason. Adopted directly from
migration 080's rationale: a skip that persists nothing means "why didn't this send" is
unanswerable from the database. Three past investigations died on that.

### 4.3 Layer 3 — re-check at claim time

Consent can be revoked between build and send (a long campaign runs for hours). The worker
re-calls `is_sendable()` **after** winning the claim and **before** calling the provider. On
failure it marks the row `skipped` with the new reason and moves on. This is the check that
makes revocation actually work.

### 4.4 Unsubscribe (dep: R4)

- **Email.** Every marketing send gets a `List-Unsubscribe` header (mailto + one-click URL)
  and a visible footer link. `GET /unsubscribe/[token]` → confirmation page →
  `POST` writes `email_consent=false`, `email_unsubscribed_at=now()`, and a
  `do_not_contact_list` row with `source='unsubscribe_link'`, `scope='marketing'`. Token is
  a signed HMAC of `(contact_id, campaign_id)`, not a raw uuid.
- **SMS.** Twilio's Messaging Service handles STOP/UNSTOP at the carrier level, but the Hub
  must mirror it: `api/twilio/inbound-sms` already receives inbound — add STOP/START/HELP
  keyword handling that writes `sms_consent=false` + a DNC row. Without the mirror the Hub
  keeps *believing* it can text someone Twilio is already blocking.
- `api/email/webhook-inbound/route.ts` already has an `unsubscribed` branch
  (lines 44-52) that writes `email_consent=false` + `email_unsubscribed_at`. Keep the
  handler, fix the column names (`unsubscribed_at` and `*_count` fields do not exist on the
  live schema).

### 4.5 Re-permission campaign (R4)

The first campaign built. Shape:

- **Audience:** every contact with a deliverable address and a defensible relationship
  (`source` in the "yes" and "verify" rows of §0.3). Explicitly **not** the scraped list.
- **Intent:** `service` (it is a consent-status enquiry to people we have a relationship
  with, not a promotion).
- **Body:** states plainly what we send, how often, and offers one button. Clicking it hits
  `GET /consent/[token]` which writes `email_consent=true`,
  `email_consent_source='double_optin'`, `email_consent_at=now()`, and evidence
  `{ip, user_agent, campaign_id, clicked_at}`.
- **Everything else is gated on its outcome.** If it converts 8 people, the honest answer is
  that bulk email stays parked and the effort belongs upstream at acquisition — which is
  what the university funnel is for.

## 5. Send pipeline

Five stages. Build is synchronous; the rest are cron-driven workers.

```
draft ──build──> building ──> scheduled ──cron──> sending ──> completed
                                              ├─> paused (manual, resumable)
                                              └─> failed (provider auth / config)
```

### 5.1 Build (`POST /api/campaigns/[id]/build`)

Staff-auth, org-scoped, admin client. Resolves the audience (§3), calls `is_sendable()` per
contact, inserts `campaign_recipients` rows (pending or skipped), sets
`status='scheduled'`. Idempotent — re-running a build is safe because
`campaign_recipients_contact_once` rejects duplicates.

### 5.2 Claim (the guard)

Adopted wholesale from 077. **Insert/update wins the claim; the DB arbitrates, not the
client.** Because rows already exist, the claim is a conditional UPDATE rather than an
INSERT:

```sql
update campaign_recipients
   set status = 'claimed', claimed_at = now(), attempt = attempt + 1
 where id in (
   select id from campaign_recipients
    where campaign_id = $1 and status = 'pending'
    order by created_at
    limit $2
    for update skip locked          -- two workers never claim the same row
 )
returning *;
```

`FOR UPDATE SKIP LOCKED` is what makes overlapping cron ticks safe. The 1-minute
`process-queue` cron in the current code has **no claim at all** — two overlapping
invocations would double-send every queued row.

**Stale-claim reaping** (from `stage-emails/route.ts:120-129`): before claiming, release
`status='claimed'` rows older than `STALE_CLAIM_MINUTES` (15) back to `pending`, capped at
`attempt < 3`. A crashed worker must not permanently strand its batch.

### 5.3 Dedupe

Three layers, in order:
1. **Build time:** `campaign_recipients_contact_once` — one row per contact.
2. **Build time:** the first row to claim a `dest_hash` for the campaign wins; subsequent
   contacts with the same normalized address get `status='skipped'`,
   `skip_reason='duplicate_address'`. Solves the 10 shared addresses.
3. **Claim time:** the partial unique index on `(campaign_id, dest_hash)` is the backstop
   if anything above is bypassed.

### 5.4 Throttle

- **Per-campaign:** `throttle_per_minute` (default 20).
- **Per-org per-day:** `org_email_daily_stats` already exists with the right shape
  (`stat_date`, `sent`, `delivered`, `opened`, `clicked`, `bounced`, `complained`). Reuse it;
  fix the column names the dead code got wrong.
- **Warm-up:** for a brand-new sending domain, cap at 50/day and grow ~1.5×/day to the
  configured limit. The existing `process-queue` warmup used `50 * 2^days`, which reaches
  51,200/day in 10 days — far too aggressive for a domain with no reputation. Replace it.
- **SMS:** Twilio Messaging Service handles per-number queueing; the Hub should still cap
  outbound per minute to keep the queue observable and avoid burning A2P throughput.

Worker batch size = `min(throttle_per_minute, daily_cap - sent_today, provider_batch_max)`.

### 5.5 Retry

- Provider **4xx** (bad address, blocked, invalid number): terminal → `failed`, no retry.
- Provider **5xx / network / timeout**: retryable → back to `pending`, `attempt++`, with
  backoff via a `next_attempt_at` column. Give up at `attempt = 3`.
- **Hard bounce** (from webhook): `bounced` + DNC row with `source='bounce_hard'`,
  `scope='all'`. Soft bounce: leave `sent`, count it, suppress after 3 in 30 days.

### 5.6 Cron

Replace the `/api/email/campaign/process-queue` entry in `vercel.json` with:

```json
{ "path": "/api/campaigns/process", "schedule": "* * * * *" }
```

One worker handles both channels; it branches to the adapter on `campaigns.channel`. Auth
via `verifyCronSecret()` (`lib/crm-server.ts:474`).

## 6. Channel adapters

A thin interface so the pipeline never knows which provider it is talking to:

```ts
interface ChannelAdapter {
  send(ctx: {
    orgId: string
    campaign: Campaign
    recipient: CampaignRecipient
    contact: CrmContact
  }): Promise<{ ok: boolean; providerMessageId?: string; error?: string; retryable: boolean }>
}
```

### 6.1 Email — Resend (new)

Currently email goes through **Google Apps Script → Gmail** (`org_settings.stage_email_script`,
`google-apps-script/Code.gs`). That is correct for a handful of stage emails and wrong for
bulk: Gmail caps at ~500-2000/day, gives no bounce/complaint feedback, no per-message
tracking, and puts the org's primary mailbox reputation at risk.

**Resend is the right call, but it is net-new and has prerequisites:**

- `resend` is **not in `package.json`** — add it.
- **Domain authentication is a hard blocker:** SPF, DKIM, and a DMARC record on the sending
  subdomain (use `mail.neuroprogeny.com`, not the apex, to isolate reputation).
- New env: `RESEND_API_KEY`. Per-org sending identity lives in `org_email_config` — extend
  it with `provider text default 'apps_script'`, `resend_from_email`, `resend_from_name`,
  `resend_domain_id`.
- Keep the Apps Script path for stage emails and 1:1. `provider` on `org_email_config`
  selects; bulk always uses Resend.
- Webhooks: `POST /api/webhooks/resend` for `delivered`/`opened`/`clicked`/`bounced`/

### 6.2 SMS — Twilio (existing)

Reuse `sendOrgSms(config, to, body, 'campaign', undefined)` from `lib/twilio-org.ts`
unchanged. It already:

- resolves the org's Twilio credentials from `org_settings.crm_twilio` with env fallback,
- routes `'campaign'` context to the `outreach`-purpose number (`CONTEXT_TO_PURPOSE`),
- prefers `messagingServiceSid` when configured (correct for bulk — it gives Twilio the
  queue and the number pool),
- attaches `statusCallback` to `/api/twilio/message-status`.

Bulk-specific additions:

- **A2P 10DLC registration is a prerequisite.** Unregistered bulk US SMS gets filtered.
  Campaign type must be registered with Twilio before any bulk send.
- **Quiet hours:** no sends outside 08:00-21:00 in the recipient's timezone. `contacts` has
  no timezone column — derive from area code as a first pass, and default to the org's
  timezone when unknown. Enforce in the worker: rows that fall outside the window stay
  `pending` rather than being skipped.
- **Segment counting:** compute GSM-7 vs UCS-2 segments at build time and surface the count
  and cost estimate in the preview. A stray em dash or curly quote silently triples cost —
  which the voice rules already forbid, conveniently.
- **STOP mirroring** per §4.4.
- **Do not unify with `crm_messages`.** Per the existing architecture note, SMS goes to
  `crm_messages` and voice to `call_logs`, and the read path merges by timestamp. Bulk SMS
  should write a `crm_messages` row *as well as* its `campaign_recipients` row, so the
  contact's conversation thread shows what we sent them. If someone replies, the existing
  inbound path already threads it correctly.

### 7.2 Campaign metrics

Roll up from `campaign_recipients` — no separate counters to drift:

```sql
create view v_campaign_stats as
select campaign_id, org_id,
       count(*)                                     as total,
       count(*) filter (where status = 'sent')      as sent,
       count(*) filter (where delivered_at is not null) as delivered,
       count(*) filter (where opened_at    is not null) as opened,
       count(*) filter (where clicked_at   is not null) as clicked,
       count(*) filter (where status = 'bounced')   as bounced,
       count(*) filter (where status = 'skipped')   as skipped,
       count(*) filter (where status = 'failed')    as failed
from campaign_recipients group by 1,2;
```

Skip reasons must be visible in the UI, grouped. "142 skipped: 130 no_consent, 8
no_address, 4 duplicate_address" is the report that would have surfaced the consent bug two
months ago.

### 7.3 Open tracking caveat

Apple Mail Privacy Protection pre-fetches images, so open rate is inflated and unreliable.
Track it, but weight **clicks** in health scoring, not opens. `calculateHealthScore()`
currently uses `openRate` only (`crm-server.ts:425`) — change it to
`max(clickRate, openRate * 0.3)` or similar when repointing.

## 8. AI composer

Extend `api/email/ai-draft` rather than adding a parallel route; add
`api/campaigns/compose` for the campaign context (audience summary instead of a single
contact).

### 8.1 Technical changes to the existing route

`ai-draft/route.ts` currently calls the API with raw `fetch`, model `claude-sonnet-4-6`,
and asks for JSON in prose then strips ``` fences with a regex. Replace with:

- **`@anthropic-ai/sdk`** — already a dependency (`^0.80.0`; bump to current).
- **Model `claude-opus-5`**, `thinking: { type: 'adaptive' }`. Copy quality matters more
  than latency here, and a campaign is drafted once and sent to hundreds.
- **Structured output** via `output_config.format` with a JSON schema for
  `{subject, body_html, body_text, preview_text}` — this removes the fence-stripping and
  `JSON.parse` failure mode entirely.
- SMS variant returns `{body, segment_count}` and is prompted for a hard 320-character
  ceiling (2 segments).

### 8.2 Voice rules — extract to a shared module

The rules are currently a partial inline fragment in one route (`ai-draft/route.ts:67-70`
covers em dashes and forward-orienting questions; the rest are absent). Extract to
`src/lib/voice.ts` and use it in the composer, the campaign composer, and any future
generation surface:

```ts
export const VOICE_RULES = `
Write in complete, flowing sentences. No fragments, no bullet-point staccato.

Never use em dashes. Use commas, semicolons, or separate sentences instead.

Do not describe the reader as broken, stuck, damaged, or dysregulated, and do not
frame the offer as fixing them. Describe what becomes available, not what is wrong.

Lead with mechanism before modality. Say what is happening in the nervous system
before naming the tool or the technique that engages it.

Frame in terms of capacity, not pathology. The reader has capacity that is not yet
online, rather than a deficit to be corrected.

HRV is a mirror, not a score. It reflects state back; it does not rank or grade the
reader. Never present it as a target to beat.

Questions orient forward toward emerging possibilities, never backward into past
failures.

Write at a 9th-grade reading level. Short words, concrete nouns, active voice.
Explain any term a reader would not already know, in the sentence where it appears.
`.trim()
```

### 8.3 Composer guardrails

- **Draft only.** The composer never sets `status` past `draft`. A human edits and launches.
- **Deterministic linter after generation** — cheap regex checks the model cannot fudge:
  em dash present, sentence-fragment ratio, banned-word list
  (`broken`, `stuck`, `fix you`, `dysregulated`, `optimize your score`), Flesch-Kincaid
  grade > 9. Show violations inline in the editor; do not auto-reject, because a human
  might have a reason.
- **Merge-tag validation:** reject a draft containing a tag `resolveMergeTags()` cannot
  resolve. Its current fallback silently strips unknown `{{...}}` (`crm-server.ts:45`),
  which turns "Hi {{firstname}}," into "Hi ," for the whole list.
- **Mandatory footer** on marketing email: physical postal address (CAN-SPAM requirement)
  and the unsubscribe link, injected server-side, not model-generated.

## 9. Org scoping / white-label

- `campaigns`, `campaign_recipients` both carry `org_id NOT NULL` with FK cascade.
- RLS: service-role writes only, mirroring `stage_email_sends` (077's lockdown block). A
  browser-writable recipient table lets a client pre-claim a slot to suppress a send, or
  delete a claim to force a duplicate.
- Read path for the UI goes through admin-client API routes that resolve the caller's org
  from `org_members`, never from a client-passed `org_id` — the 067 authorization shape
  already used by `stage-emails/route.ts:45-54`.
- Sending identity is per-org: Resend domain per org, Twilio number pool per org
  (`crm_twilio_numbers` already maps this). Neuro Progeny and Sensorium must never share a
  sending reputation.
- `email_sends` gets the `org_id` it currently lacks (§2.5) — today it cannot be scoped at
  all.
