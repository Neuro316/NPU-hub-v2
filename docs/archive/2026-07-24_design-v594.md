## PART 0: THE REACHABILITY BLOCKER (read this before anything else)

This is the finding that decides whether the rest of the document matters.

### 0.1 Verdict on `email_consent`

**`contacts.email_consent` is `boolean NOT NULL DEFAULT false`, and nothing in the system has ever written a consent timestamp. The false values are absence of data, not opt-outs.**

Introspected from `pg_catalog` (not `information_schema`, per the standing craft rule):

| Column | Type | Default | Not null |
|---|---|---|---|
| `email_consent` | boolean | `false` | yes |
| `email_consent_at` | timestamptz | none | no |
| `email_unsubscribed_at` | timestamptz | none | no |
| `sms_consent` | boolean | `false` | yes |
| `sms_consent_at` | timestamptz | none | no |

Live distribution across all 306 contacts:

| Measure | Count |
|---|---|
| Total contacts | 306 |
| Has a non-empty email | 128 |
| `email_consent = true` | 27 |
| `email_consent = false` | 279 |
| **`email_consent_at` populated** | **0** |
| **`email_unsubscribed_at` populated** | **0** |
| `sms_consent = true` | 8 |
| `sms_consent_at` populated | 2 |
| Has a non-empty phone | 56 |

The decisive numbers are the two zeros.

**Zero contacts have ever recorded an unsubscribe.** No one opted out. The 279 false rows are the column default, untouched, for every contact created by every import, scrape, Stripe webhook, quiz sync, and inbound call path.

**Zero contacts have a consent timestamp, including all 27 whose flag is true.** So even the true values carry no provenance. Whatever wrote `email_consent = true` did not write `email_consent_at`, which means the consent-capture path is not a consent-capture path at all. It is a checkbox in an admin form.

The distribution confirms this. All 27 true values sit on contacts entered by hand: 22 with a null source (manual creation), plus one each from `Website`, `Podcast`, `Workshop`, and two from `Other`. Every single automated source has zero consents: `xregulation` (24 contacts), `media_appearance` (17), `Import` (11), `neuroreport` (4), `stripe` (2), `inbound_call` (2), and the roughly 130 social-scrape rows created 2026-03-11 and 2026-03-12.

There is also direct evidence that at least one of the 27 is a test artifact rather than a real opt-in. Cameron's own contact (`4cb236f6`) was flipped to `email_consent = true` during the Equipment stage-email test, with a standing note to revert it to false afterward. The flag is being used as a test switch.

**Consequence: `email_consent` is not a record of user intent. It is an unwritten field. Treating it as an opt-out signal would be a factual error about your own data.**

### 0.2 The inverse problem: `do_not_contact`

`contacts.do_not_contact` is `boolean DEFAULT false`, and **92 of 306 contacts are true**, while the separate `do_not_contact_list` table has **zero rows**.

Fifty of those 92 were created on 2026-03-11, the social-prospecting scrape day. This flag was set in bulk by an import path, not by 92 people asking not to be contacted. It is the mirror image of the consent defect: one field defaults false and was never written, another defaults false and was written indiscriminately.

**Eight contacts have `do_not_contact = true` AND `email_consent = true` simultaneously.** Those are flatly contradictory and need adjudication before any send.

Two suppression surfaces exist (`contacts.do_not_contact` and the empty `do_not_contact_list`) with no documented precedence between them. The design below makes precedence explicit.

### 0.6 The `email_sends` logging gap is not a logging bug

`email_sends` has zero rows. So does `email_campaigns`. And `email_sends.campaign_id` is `NOT NULL` with `FOREIGN KEY (campaign_id) REFERENCES email_campaigns(id) ON DELETE CASCADE`.

`email_sends` is not a general send ledger that is failing to log. It is a campaign recipient ledger that structurally cannot hold a row unless a campaign exists, and no campaign has ever existed. Every stage email, every 1:1 email, every transactional send is architecturally excluded from it.

So `crm-server.ts:420` reading `email_sends` for engagement scoring is reading a table that can only ever be populated by the exact feature that got parked. **The engagement scoring gap and the parked campaign feature are one defect, not two.** Pointing engagement scoring at `email_sends` and then shipping campaigns would still score every contact at 0% for all non-campaign contact, which is nearly all of it.

This is the strongest argument in the document for the central architectural recommendation in Part 2: one ledger for every outbound message, regardless of what triggered it.

## PART 1: THE DECISION THAT UNBLOCKS EVERYTHING

Before the build session runs, one question needs an answer, and it is a business and legal question rather than an engineering one.

**A boolean was asked to carry a legal concept, and that is why the field is empty.**

"May I send to this person" has several different valid answers with different legal bases, and the schema can only express one of them:

- Express written consent (required for marketing SMS under the TCPA, and the standard under GDPR and CASL)
- An existing business relationship, such as a customer, participant, or purchaser
- Commercial email under CAN-SPAM, which in the US is an opt-out regime rather than an opt-in one, requiring accurate headers, a physical address, and a working unsubscribe
- Transactional or relationship messages, which sit outside marketing rules entirely

I am not a lawyer and this is not legal advice; the CAN-SPAM and TCPA determination for Neuro Progeny and for Sensorium should go to counsel, particularly because Sensorium is a clinical entity and clinical context raises the stakes. But the engineering consequence is clear and it does not depend on how counsel rules.

**Recommendation: replace the single boolean with a recorded sending basis per contact per channel.** The pipeline then asks "what is my basis for reaching this person on this channel, and what is the evidence" instead of "is a flag true." Under an opt-out email model, most of the 279 become reachable with a documented basis and a working unsubscribe. Under an opt-in model, they do not, and the answer is a capture program rather than a campaign feature. Either way the schema in Part 2 holds, and either way SMS stays strictly opt-in because the TCPA leaves no room.

### Decision table for Cameron

| # | Decision | Options | Blocks |
|---|---|---|---|
| D1 | Email sending basis | Strict opt-in, or opt-out with documented basis plus unsubscribe | Whether the audience is 9 or roughly 118 |
| D2 | The 8 contradictory rows (`do_not_contact` and `email_consent` both true) | Suppress all 8, or review individually | Recipient resolution correctness |
| D3 | The 92 `do_not_contact = true` rows | Confirm as intentional, or treat the 50 from the 03-11 scrape as an import artifact and reset | Audience size |
| D4 | `sequences` versus `campaign_automations` | Pick one drip engine, retire the other | Part 2 data model |
| D5 | `org_email_config` Gmail path | Retire the Apps Script transport, keep the throttle and warmup concepts | Part 3 throttle |
| D6 | Bulk SMS at all | Given the TCPA bar and a current audience of zero, is this phase two? | Scope of the build |

**My read on D6:** bulk SMS is the smaller and riskier half. The consent bar is higher, the audience is zero today, and the 1:1 Twilio surface already carries the real conversational load. I would build the ledger and the adapter seam so SMS drops in cleanly, then ship email first and hold SMS until there is a consent capture path producing real opt-ins.

## PART 2: DATA MODEL

### 2.1 Central recommendation

**Do not build a campaign send ledger. Build one outbound message ledger and let campaigns, sequences, stage emails, and manual sends all write to it.**

Rationale, drawn from Part 0: `email_sends` is unreachable to non-campaign sends, `sequences` has no ledger at all, and `stage_email_sends` is the only one that works. Three parked ledgers is how engagement scoring ended up reading an empty table. One ledger means engagement scoring, deliverability rollups, suppression, and frequency capping each have exactly one source of truth, permanently.

### 2.2 New table: `message_sends`

A generalization of `stage_email_sends`, preserving every pattern that migration 077 and 080 proved.

```sql
create table message_sends (
  id                  uuid primary key default gen_random_uuid(),
  org_id              uuid not null references organizations(id) on delete cascade,
  contact_id          uuid not null references contacts(id) on delete cascade,

  channel             text not null check (channel in ('email','sms')),

  -- what triggered this send
  source_kind         text not null check (source_kind in ('campaign','sequence','stage','manual','transactional')),
  source_id           text,          -- campaign_id, sequence_id, pipeline_id
  source_step_id      text,          -- stage_id + email_id, or sequence step id

  -- generalization of stage_email_sends' (stage_id, email_id) uniqueness
  dedupe_key          text not null,

  to_address          text not null, -- normalized: lower(trim(email)) or E.164
  status              text not null default 'sending'
                      check (status in ('sending','sent','failed','skipped','suppressed','bounced')),
  skip_reason         text,

  -- consent proof captured at claim time, immutable
  consent_basis       text not null,
  consent_evidence_id uuid references consent_events(id),
  consent_snapshot    jsonb not null default '{}'::jsonb,

  external_message_id text,          -- Resend id or Twilio sid
  crm_message_id      uuid references crm_messages(id) on delete set null,
  error_code          text,
  error_message       text,
  attempts            integer not null default 0,

  claimed_at          timestamptz not null default now(),
  sent_at             timestamptz,
  delivered_at        timestamptz,
  opened_at           timestamptz,
  clicked_at          timestamptz,
  bounced_at          timestamptz,
  complained_at       timestamptz,
  unsubscribed_at     timestamptz
);

-- the 077 pattern, generalized: one live send per contact per channel per logical message
create unique index message_sends_once
  on message_sends (contact_id, channel, dedupe_key)
  where status in ('sending','sent');

-- the 077 stale-claim reaper
create index message_sends_stale
  on message_sends (status, claimed_at)
  where status = 'sending';

create index message_sends_contact  on message_sends (contact_id, claimed_at desc);
create index message_sends_source   on message_sends (source_kind, source_id, status);
create index message_sends_org_day  on message_sends (org_id, sent_at desc);
```

Notes on specific choices:

- **`org_id NOT NULL` and directly on the row.** `email_sends` has no `org_id` and would have to reach through `campaign_id` to be scoped. Given the R0.4 cross-tenant findings, no new table should require a join to know its tenant.
- **`dedupe_key` as text, composed by the caller.** `stage:{stage_id}:{email_id}`, `campaign:{campaign_id}`, `sequence:{sequence_id}:{step_id}`, `manual:{uuid}`. This is the single generalization that lets one partial unique index serve all four send sources.
- **`skipped` and `suppressed` sit outside the unique index**, exactly as migration 080 did, so a skip does not block a later legitimate send.
- **`consent_snapshot` is immutable proof.** If a contact later revokes, the record of what the basis was at send time survives. This is what makes a complaint defensible.
- **`crm_message_id`** links a bulk SMS to the conversation row it created, so the thread stays truthful (see 4.2).

### 2.3 New table: `consent_events` (append-only)

```sql
create table consent_events (
  id            uuid primary key default gen_random_uuid(),
  org_id        uuid not null references organizations(id) on delete cascade,
  contact_id    uuid not null references contacts(id) on delete cascade,
  channel       text not null check (channel in ('email','sms')),
  action        text not null check (action in ('granted','revoked')),
  basis         text not null check (basis in
                  ('express_consent','double_optin','existing_business_relationship',
                   'transactional','import_asserted','manual_admin')),
  method        text not null,      -- 'web_form','checkout','quiz','reply_stop','admin_ui','import'
  evidence      jsonb not null default '{}'::jsonb,
                -- ip, user_agent, form_url, exact checkbox text shown, campaign_id, message body for STOP
  source_ref    text,
  actor_id      uuid references auth.users(id),
  occurred_at   timestamptz not null default now(),
  created_at    timestamptz not null default now()
);

create index consent_events_lookup on consent_events (contact_id, channel, occurred_at desc);
```

Append-only. Never updated, never deleted. `contacts.email_consent` and `sms_consent` remain as denormalized read caches, but become **derived**: written only by a trigger off this table, never by application code. That single change makes the current failure mode (a form writes the flag and forgets the timestamp) structurally impossible, because the timestamp and the evidence are the write.

The `evidence` jsonb should capture the exact checkbox text shown at the moment of consent. When someone complains two years later, "we have a boolean" is not a defense and "here is the sentence they agreed to, the URL, and the timestamp" is.

### 2.4 Extending `email_campaigns` into `campaigns_v2` shape

`email_campaigns` is close. Rather than a new table, add:

```sql
alter table email_campaigns
  add column channel text not null default 'email' check (channel in ('email','sms')),
  add column sms_body text,
  add column audience_query jsonb not null default '{}'::jsonb,
  add column audience_snapshot_at timestamptz,
  add column required_basis text[] not null default '{}',
  add column throttle_per_hour integer,
  add column voice_lint_status text not null default 'unchecked'
      check (voice_lint_status in ('unchecked','passed','failed','overridden')),
  add column voice_lint_report jsonb,
  add column approved_by uuid references auth.users(id),
  add column approved_at timestamptz,
  add column test_send_at timestamptz;
```

`filter_tags`, `filter_stages`, and `exclude_tags` already exist and stay. `audience_query` holds the richer segment definition; `audience_snapshot_at` records when the recipient list was materialized, so a campaign edited mid-send does not silently change its own audience.

### 2.5 New table: `campaign_recipients`

Materialized audience, resolved once at launch, so the send loop is a scan over a fixed list rather than a repeated query against live contacts.

```sql
create table campaign_recipients (
  id             uuid primary key default gen_random_uuid(),
  org_id         uuid not null references organizations(id) on delete cascade,
  campaign_id    uuid not null references email_campaigns(id) on delete cascade,
  contact_id     uuid not null references contacts(id) on delete cascade,
  to_address     text not null,
  consent_basis  text not null,
  consent_evidence_id uuid references consent_events(id),
  state          text not null default 'pending'
                 check (state in ('pending','claimed','sent','failed','suppressed','skipped')),
  suppress_reason text,
  merge_data     jsonb not null default '{}'::jsonb,
  created_at     timestamptz not null default now()
);

create unique index campaign_recipients_once on campaign_recipients (campaign_id, contact_id);
create index campaign_recipients_pending on campaign_recipients (campaign_id) where state = 'pending';
```

The last index mirrors `idx_sends_queued` on the existing `email_sends`, which was already the right idea.

### 2.6 Suppression: one function, explicit precedence

Reconcile the two suppression surfaces with a single resolver that every path calls.

```sql
create or replace function is_suppressed(p_contact_id uuid, p_channel text)
returns table (suppressed boolean, reason text)
language sql stable as $$
  -- precedence, highest first:
  -- 1. contacts.do_not_contact
  -- 2. do_not_contact_list match on normalized email or phone
  -- 3. hard bounce or spam complaint in message_sends
  -- 4. most recent consent_events row for this channel is 'revoked'
  ...
$$;
```

Precedence is not negotiable and must live in one place. `do_not_contact` always wins over consent, which resolves the 8 contradictory rows deterministically as suppressed, pending D2.

## PART 3: SEND PIPELINE

Reuse the machinery that already works rather than inventing a second one.

### 3.1 What migration 077 and 080 already proved

From the stage-email implementation, verified live in the indexes:

- `stage_email_sends_once`: partial unique on `(contact_id, stage_id, email_id) WHERE status IN ('sending','sent')`. The insert *is* the lock. Two concurrent workers cannot both claim the same send, because the second insert violates the index.
- `stage_email_sends_stale`: `(status, claimed_at) WHERE status = 'sending'`, driving a 15-minute stale-claim reaper for sends that died between claim and provider response.
- `status = 'skipped'` with a reason, deliberately outside the unique index.
- A `force: true` escape hatch for deliberate re-sends.
- Server-authoritative content: the route ignores client-passed bodies and renders from the stored template.

Every one of these generalizes without modification. The build session should treat 077 as the reference implementation and not redesign the claim.

### 3.2 Pipeline stages

```
draft
  -> voice lint (Part 7)
  -> audience resolve       (writes campaign_recipients, stamps audience_snapshot_at)
  -> preflight report       (eligible / suppressed / malformed, shown to Cameron before launch)
  -> test send              (to a verified internal address, required before launch)
  -> approve                (human gate, records approved_by and approved_at)
  -> queued
  -> sending                (worker loop)
  -> completed | failed | cancelled
```

The preflight report is the feature that would have surfaced this entire blocker months ago. It should state plainly: "This campaign will reach 9 of 306 contacts. 279 have no recorded sending basis, 92 are suppressed, 4 have malformed addresses." Make the audience visible before the send, every time.

### 3.3 Claim, throttle, retry

**Claim.** One worker pass claims a bounded batch:

```sql
update campaign_recipients
   set state = 'claimed'
 where id in (
   select id from campaign_recipients
    where campaign_id = $1 and state = 'pending'
    order by created_at
    limit $2
    for update skip locked
 )
returning *;
```

`FOR UPDATE SKIP LOCKED` allows multiple workers. Then per recipient, insert into `message_sends` with `status = 'sending'`; a unique violation on `message_sends_once` means someone else has it, so skip silently. Same shape as 077.

**Throttle.** Two limits, both enforced server-side:
- Per-org daily cap, incremented against `org_email_daily_stats` (already exists, correct shape).
- Per-campaign `throttle_per_hour`, so a batch of 3,000 does not go out in ninety seconds and torch domain reputation.

Retire the `org_email_config` Gmail and Apps Script fields (D5), keep `daily_send_limit`, `sends_today`, `sends_reset_at`, and the warmup fields, generalized per channel.

**Retry.** Reuse `scheduled_jobs`, which already has atomic claim, `attempts`, and `last_error`. Do not build a second queue. Retry only on transient provider errors (429, 5xx, timeout). Never retry a hard bounce, an invalid address, or a Twilio opt-out error; those write terminal status and feed suppression.

**Reaper.** A periodic pass over `message_sends` where `status = 'sending' AND claimed_at < now() - interval '15 minutes'`, resolving against the provider by `external_message_id` where one exists, marking failed where none does. Directly ported from 077.

### 3.4 Dependency on the blocker

Every stage above is buildable today. The **audience resolve** stage is the one that produces nothing useful until Part 1 D1 is decided, because it reads the sending basis. Build order in Part 8 accounts for this.

## PART 4: CHANNEL ADAPTERS

A single `SendAdapter` interface so the pipeline never branches on channel:

```ts
interface SendAdapter {
  channel: 'email' | 'sms';
  validate(address: string): { ok: boolean; normalized?: string; reason?: string };
  send(input: SendInput): Promise<{ externalId: string } | { error: SendError }>;
  classifyError(err: unknown): 'transient' | 'permanent' | 'suppress';
}
```

### 4.1 Email adapter (Resend)

- `validate` normalizes to `lower(trim(email))`, strips a `mailto:` prefix, and rejects anything failing basic shape. Rachel Kimmel's record is the live test case.
- Every send carries a `List-Unsubscribe` header and a one-click unsubscribe URL with a signed token. Non-negotiable, and it is what makes an opt-out basis defensible if D1 goes that way.
- Store the Resend id in `external_message_id`, matching the `email_resend_id` convention already established in `nr_quiz_results`.
- Webhook endpoint receives `delivered`, `opened`, `clicked`, `bounced`, `complained`. Dedupe through `webhook_events`, which already has the dedupe gate built for Stripe.
- `bounced` (hard) and `complained` write suppression immediately and a `consent_events` revoke row.
- The `email_from_identity` flag parked on the platform assessment submit route is the same concern here: sender identity must be org-scoped, not hardcoded. Note that `email_templates.from_email` currently defaults to `admin@sensoriumneuro.com`, which is a white-label leak waiting to happen for Neuro Progeny sends.

### 4.2 SMS adapter (Twilio)

Reuses the existing account, `receiverIdentity(orgId)`, and outbound caller ID from the completed 1:1 build. Load-bearing constraints from that build carry over unchanged and must not be re-litigated: `forward_number` stays retired, and `receiverIdentity(orgId)` remains the single source of the client identity string.

- `validate` normalizes to E.164. Given that 54 of 56 phones are non-conforming, normalization is a prerequisite, not a nicety.
- **Bulk SMS writes to `crm_messages`, not to a parallel table.** When a recipient replies, the reply lands in the existing conversation thread, and if the outbound campaign message is not in that thread, the softphone shows a reply to nothing. `message_sends.crm_message_id` links the accounting row to the conversation row. `crm_messages` already has the right dedupe primitive in `uq_crm_messages_twilio_sid`.
- Inbound `STOP`, `UNSUBSCRIBE`, `QUIT` must write a `consent_events` revoke row and a suppression entry, not merely a Twilio-side block, so the Hub's own view of consent stays accurate.
- Quiet hours by recipient timezone, and a per-campaign send window. Bulk SMS at 6am is a complaint generator.
- **Blocked on `crm_messages` org scoping.** Per the R0.4 plan, `crm_messages` has no `org_id` in its policy path and must be scoped through `conversations`. Bulk SMS writing to `crm_messages` at volume before that is fixed would multiply the exposure surface. **Bulk SMS must not ship before R0.4 Stage 3.**

## PART 5: CONSENT ENFORCEMENT

The constraint was "structurally impossible to send without valid consent." Application-level checks do not achieve that, because the next route someone writes will forget. Four layers, each independent:

**Layer 1: derived flags.** `contacts.email_consent` and `sms_consent` become trigger-maintained from `consent_events`. Revoke `UPDATE` on those columns from the application role. A form can no longer set a flag without writing evidence, because the flag is not writable.

**Layer 2: database-enforced send gate.** A `BEFORE INSERT` trigger on `message_sends` that rejects any row with `status = 'sending'` unless a valid, non-revoked consent basis exists for that contact and channel, and unless `is_suppressed()` returns false. A rogue route, a Claude Code mistake, or a manual `INSERT` in the SQL editor all fail at the database. This is the layer that makes the guarantee real.

**Layer 3: resolver function.** `campaign_eligible_recipients(campaign_id)` as `SECURITY DEFINER`, the only supported way to build an audience. It re-checks consent and suppression at resolve time and again at claim time, because a revoke arriving mid-campaign must take effect on the remaining sends.

**Layer 4: RLS, and the R0.4 trap.** All new tables get org scoping via `org_id IN (SELECT user_org_ids())`, never the correlated-subquery form that produced the 033b defect across 50 tables. And per the durable rule, every `UPDATE` policy on these tables gets an explicit `WITH CHECK`, not just a `USING` clause.

Channel separation is absolute throughout. Email consent never satisfies an SMS send. The `channel` column on `consent_events` is part of every lookup, and there is no code path where one channel's basis is read for the other.

## PART 6: ENGAGEMENT TRACKING

**The fix is to repoint `crm-server.ts:420` from `email_sends` to `message_sends`.** Once every outbound message lands in one ledger, engagement scoring sees stage emails, sequence steps, campaign sends, and manual sends alike, and a contact's score reflects their actual history rather than their campaign history.

Rollups: a small job aggregates `message_sends` into `org_email_daily_stats` per org per day. That table exists and is correctly shaped; it just has nothing to aggregate yet.

Suggested engagement signals, per contact: sends in the last 90 days, open rate, click rate, last engagement timestamp, bounce and complaint flags. Bounces and complaints should decay a contact toward suppression automatically rather than waiting for someone to notice.

Backfill: the 6 `stage_email_sends` rows migrate into `message_sends` with `source_kind = 'stage'` and a composed `dedupe_key`. Small enough to verify by eye. Keep `stage_email_sends` read-only afterward rather than dropping it, until the new path is live-tested.

There is a related open item from the last Hub session that should be resolved in the same pass: the read-only investigation mapping every email send currently linked to Enrolled-pipeline movement, distinguishing wired-and-live from stub. Two paths writing sends under different assumptions is how a duplicate-send incident starts.

## PART 7: AI COMPOSER AND VOICE RULES

### 7.1 Voice rules as a gate, not a prompt

Prompt instructions drift. The rules should be enforced as a lint that blocks the campaign from leaving draft.

`voice_lint(text)` checks, each returning a located finding:

| Rule | Check |
|---|---|
| No em dashes | Literal scan for the character, plus the double-hyphen substitute |
| Complete flowing sentences | Flag fragments and staccato runs, no verb-less sentences |
| No negation of brokenness | Pattern list: "not broken", "nothing wrong with you", "isn't damaged". Preferred replacement surfaced inline: "your nervous system has never made a mistake" |
| Mechanism before modality | Heuristic: first mention of a modality should not precede the first mention of a mechanism |
| Capacity over pathology | Banned-term list, shared with the AI Coach's existing list rather than maintained twice |
| HRV as mirror, not score | Flag "HRV" within a short window of "score", "good", "bad", "high", "low" as a rating |
| Questions orient forward | Flag interrogatives containing past-failure framing |
| Reading level | Flesch-Kincaid grade above 9 fails |

The banned-terms list already exists for the AI Coach, and the coherence audit found the Insights page violating it. Sharing one list across both surfaces means a fix in one place fixes both.

`voice_lint_status` on the campaign is `unchecked`, `passed`, `failed`, or `overridden`. Only `passed` or `overridden` may transition out of draft, and an override records who and why.

### 7.2 Composer behavior

- Drafts subject, preview text, and body from a brief plus recipient segment context.
- Returns the lint report alongside the draft, so revision is one loop rather than a surprise at launch.
- SMS composer additionally enforces segment count, a required opt-out line, and per-channel length.
- Merge tags render against `campaign_recipients.merge_data`, with a mandatory fallback per tag. Note the trailing-whitespace-in-first-name problem from 0.3: without a trim in the merge renderer, greetings read `Hi Melissa ,`.
- The composer never sees the recipient list. It writes copy; it does not select an audience.

## APPENDIX: VERIFICATION QUERIES

Every claim in Part 0 came from read-only queries against production. The load-bearing ones, for re-running after any remediation:

```sql
-- consent column defaults (pg_catalog, never information_schema)
select c.relname, a.attname, pg_get_expr(d.adbin, d.adrelid) as default_expr, a.attnotnull
  from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
  join pg_attribute a on a.attrelid = c.oid and a.attnum > 0 and not a.attisdropped
  left join pg_attrdef d on d.adrelid = c.oid and d.adnum = a.attnum
 where n.nspname = 'public' and c.relname = 'contacts'
   and a.attname in ('email_consent','sms_consent','do_not_contact');

-- the two zeros that decide the question
select count(*) filter (where email_consent_at is not null)      as consent_timestamps,
       count(*) filter (where email_unsubscribed_at is not null) as unsubscribes
  from contacts;

-- true sendable audience, email
select count(*) from contacts
 where email_consent
   and email is not null and btrim(email) <> ''
   and not do_not_contact
   and email ~* '^[^@\s]+@[^@\s]+\.[a-z]{2,}$';

-- true sendable audience, sms
select count(*) from contacts
 where sms_consent and not do_not_contact and phone ~ '^\+1[0-9]{10}$';

-- the contradictions
select id, first_name, last_name, email, source
  from contacts where do_not_contact and email_consent;
```
